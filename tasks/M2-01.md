## Plan
Approved by Sham on 2026-11-16 with the three recommendations: dev runs the real sign-in (screens in a follow-up, M2-14), Secrets Manager for the Massive key, dev without a NAT gateway.

What I found:
- The S3 adapters already work against real S3 (no endpoint, default credentials); only the wiring (`apps/hydration/src/stores.ts`, `contexts/data/src/adapters/local-data-layer.ts`) always fills in MinIO's address and keys.
- DynamoDB already has an `"aws"` mode, and the table is created by CDK there (`ensureUsersTable` runs only locally).
- Redis keys already carry hash tags (`bars:{BTCUSD:5m}`), so ElastiCache Serverless (cluster mode behind one endpoint) works with the current client; it needs TLS (`rediss://`).
- The apps run TypeScript through `tsx`; there are no Dockerfiles yet.

1. **`infra/` (new Nx project `@aia/infra`, tag `type:infra`):** a CDK app (`aws-cdk-lib`, `constructs`, `aws-cdk` CLI, pinned) with one stack per environment from `infra/environments.ts`: `dev` (account 448554876487, us-east-1) now; `staging` and `prod` added once their account numbers are known. The stack:
   - **Network:** VPC over 2 AZs; public subnets for the ALB-facing tasks in dev (no NAT gateway, about $33 a month saved), private subnets with a NAT gateway for staging and prod (a per-environment switch); isolated subnets for the cache; free gateway endpoints for S3 and DynamoDB.
   - **S3:** `raw` (versioned, kept forever: never deleted by a stack removal, rule 3), `cooked` (rebuildable, also kept), `chart` (the built chart). All encrypted, public access blocked, TLS only.
   - **DynamoDB:** the users table (`pk`/`sk`, TTL on `ttl`, on demand, point-in-time recovery), kept on removal.
   - **ElastiCache Serverless (Valkey engine):** TLS, reachable only from the two services' security groups.
   - **ECS on Fargate, one container image for both apps:** `platform` (port 8080, `AIA_DYNAMODB_ENDPOINT=aws`, `AIA_S3_ENDPOINT=aws`, `rediss://` URL, the plans and safeguards files from `config/`) behind an **internal ALB**; `hydration` runs `live` (1 task, every instrument, one writer per instrument). Backfill and gap repair run as one-off tasks from the same image (`pnpm aws:task backfill ...`) until scheduling is decided.
   - **CloudFront**, one address for everything: the chart from S3, and `/bars`, `/instruments`, `/indicators`, `/plan`, `/auth`, `/live` (WebSocket) and `/mcp` to the ALB through a CloudFront **VPC origin**, so the ALB is never public and no domain or certificate is needed yet (the `*.cloudfront.net` address).
   - **Secrets:** `MASSIVE_API_KEY` in AWS Secrets Manager, read by the hydration task only; a script puts it there from `.env` without printing it.
   - **Logs:** CloudWatch log groups with 30 days' retention.
   - **Least privilege:** platform reads raw and cooked and uses the users table; hydration writes raw (no delete) and cooked; neither can do anything else.
   - Fastify `trustProxy` set for the ALB (T-06 notes the client address must come from it).
2. **Small app changes:** `AIA_S3_ENDPOINT=aws` means real S3 with the task's own credentials, like DynamoDB's `"aws"` (the two wiring files above, with tests). No business rule changes.
3. **`Dockerfile`** (Node 22, pnpm, the workspace, `tsx`), built locally to prove it starts.
4. **Checks without AWS:** Vitest tests on the synthesized template (CDK assertions): raw bucket retained, versioned and not public; ALB internal; nothing public except CloudFront; no secret in plain environment variables; each task role's permissions exactly as above. `pnpm synth` script, and a CI job that runs it (no AWS credentials needed).
5. **Deploy, once access exists:** `pnpm deploy:dev` (CDK deploy, then chart upload and CloudFront refresh). Not run in this task until the admin grants access; the card and PR say so.
6. **Docs:** architecture (AWS section), decision record (F-01 narrowed: dev exists in code, not yet deployed; dev without NAT; Valkey; dev auth question below), owner inputs: new item "AWS deploy access on dev" blocking the deploy half of M2-01.

**Surprises.**
- Fastify 5.12 ignores a numeric `trustProxy` (fails closed, by design), so the trusted proxies are given as the VPC range; CloudFront's VPC origin and the ALB both connect from inside it.
- The organisation's service control policy denies `eu-north-1` entirely; `us-east-1` works.
- aws-cdk-lib's types do not compile under `exactOptionalPropertyTypes`; `infra/tsconfig.json` turns that one option off.
- CDK wanted to look up availability zones during synth; the stack names them itself (`environments.ts`, `zones`).
- Raw history in AWS starts empty: the first deploy needs backfills (step 3).
