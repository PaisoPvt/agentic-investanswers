## Plan
What I found (M4-06's first acceptance run, 2026-11-21):
- `pnpm rebuild-check` failed locally: 1,293 differences, all from 14 Nov 2026, both instruments, every intraday timeframe.
- Raw day files for 14 and 15 Nov were written by a backfill on 16 Nov, after `pnpm live` had already compacted those days from its live minutes, which covered only part of each day. The stored 4h bar of 14 Nov has about half the rebuilt volume.
- `pnpm backfill` writes raw day files and drops cached windows, but never re-cooks. Gap repair re-cooks the months it touched (`repairAndRecook`, M1-09); backfill does not.
- AWS dev is probably affected the same way: live started compacting on 19 Nov while backfills ran.

Steps:
1. **`backfillAndRecook`** (`apps/hydration/src/backfill-and-recook.ts`, beside `repairAndRecook`): run the backfill, collect the months of the days it **stored** (not skipped or empty), and cook each of those months whole from raw for crypto (stocks are cooked from M1-08). It returns the report and the months re-cooked.
2. **`pnpm backfill`** uses it and prints `re-cooked 2026-11` per instrument. The cache windows are dropped after the re-cook, as now.
3. **Test** (`backfill-and-recook.test.ts`), today's case in memory:
   - a day is cooked from partial live minutes;
   - the backfill stores the full day file;
   - before the fix, `RebuildCheck` reports differences; after `backfillAndRecook`, it passes.
   Also: skipped days re-cook nothing, and stocks re-cook nothing.
4. **Repair:**
   - **locally:** `pnpm cook --from 2026-11-01` for BTC and ETH, then `pnpm rebuild-check` must pass;
   - **AWS dev**, after tomorrow's deploy: the one-off tasks `pnpm aws task dev cook --from 2026-11-01`, then `pnpm aws task dev rebuild-check`.
5. **Docs:** architecture (backfill now re-cooks; the one race left, see below), card handoff.

**The race left:**
- **How it happens:** at a UTC midnight, `pnpm live`'s compactor re-cooks the day just ended. If a backfill stores that same day while the compactor is between reading raw and writing, the compactor's partial result can land last.
- **Why it's rare:** backfill only fetches settled days, at least a day old, so this needs a backfill of the day that has just ended, in the seconds after midnight.
- **Why it's caught:** the rebuild check in `pnpm acceptance` would show it.
- **What I propose:** document it and not lock for it in the MVP. The same compactor reads raw once per day.

Not in this task: the guard against two `pnpm live` writers (M3-05's surprise), which remains a separate follow-up.
