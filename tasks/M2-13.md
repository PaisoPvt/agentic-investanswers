## Plan
What I found:
- `contexts/preferences` exists (tag `layer:product`, AGENTS.md "Saved chart preferences per user") but is empty.
- The users table (`pk`/`sk`, already granted read and write to the platform) holds accounts, sessions and agent keys. One more item per account, `ACCOUNT#<id>` / `PREFS`, fits it with no CDK change. Access owns the table today; preferences would share it by name (the table name is passed in), not through access's internals. Audit, by contrast, has its own table.
- The chart picks the first instrument and 1m at load (`App.tsx`), kept only in React state. It already knows the account (`AuthGate` → `session.account.id`).
- No theme exists yet (M2-12, deferred by Sham). The field is saved and returned now, and M2-12 applies it.

Steps:
1. **Domain** (`contexts/preferences/src/domain`): `ChartPreferences { instrument?, timeframe?, theme?: 'light' | 'dark' }` and a pure `parsePreferences(input)` that rejects unknown fields, bad timeframes and over-long symbols. No check against plans here: the chart decides at load whether a saved instrument and timeframe are still allowed, and falls back to the default otherwise.
2. **Application**: `PreferencesStorePort { get(accountId), put(accountId, prefs) }`; use cases `GetPreferences` and `SavePreferences` take a principal. Humans only: an agent key gets 403 `read_only` on save and 404 on read (preferences are a person's).
3. **Adapters**: `MemoryPreferencesStore` and `DynamoPreferencesStore` (table name and client passed in; `@aws-sdk/client-dynamodb` is already a dependency of access and audit, so not new to the repo). One contract test runs both, the DynamoDB half against DynamoDB Local as the other stores do.
4. **Contract** (`@aia/client-contract`): `ChartPreferencesDto` and `GET /preferences` → 200 `{ instrument?, timeframe?, theme? }`, `PUT /preferences` (whole object) → 204, 400 `invalid_preferences`, 401, 403. **This adds to the contract between the chart and the platform: Sham's approval needed.**
5. **Platform**: `preferences-routes.ts`, mounted always (developer access uses the local principal and the memory store), with the same per-principal rate limit as other writes; wired in `main.ts` to DynamoDB when `AIA_DYNAMODB_ENDPOINT` is set. Add `/preferences` to `API_PATHS` (CloudFront) and the Vite proxy; the existing test that compares `API_PATHS` with the routes covers it.
6. **Chart**: `PlatformClient.preferences()` / `savePreferences()`. At load, after the instrument list, use the saved instrument and timeframe if the plan still includes them; save on change (debounced, last write wins; a failed save is logged and never blocks the chart).
7. **Tests**: domain unit tests, store contract tests, route tests (401, 403 for an agent key, 400, round trip), a chart unit test for the fallback, and an e2e in the `sign-in` project: user A picks ETHUSD 1h, reloads, gets ETHUSD 1h; user B still gets the default.
8. **Docs**: architecture (preferences item in the users table); decision record: a new postponed entry "theme is saved but not shown until M2-12". T-10 (drawings and watchlists in the browser) stays as is, noted as the natural next use of this store.

Verify: `pnpm check`, `pnpm e2e`. Bars are not touched, so no parity or rebuild check.

Approved by Sham 2026-11-23, on condition of no performance lag, no security issue and no later bottleneck:
- Performance: preferences are fetched in parallel with `GET /instruments` (never in series), one DynamoDB read by key; saves are debounced (1 s) and never block the chart.
- Security: signed-in only, humans only, unknown fields refused, body capped at 1 KB, counted against the per-user request limit.
- Scale: one item per account in an on-demand table, keyed by account, so load spreads with users.

## Handoff
**Done (2026-11-23):** all eight steps, as planned. Two choices made while building:
- Saves count against the caller's existing request limit (`checkReads`), not a new rate-limit bucket: a new bucket would change the access context's safeguards config and every test that builds it, for no gain (the chart saves at most once a second).
- The developer-access e2e server does not mount `/preferences`: every test there is the same user, so one test's choice would open the next one's chart. The chart then opens on the defaults (GET answers 404, caught). The `sign-in` project, one account per test, covers the feature.

**Verified:** `pnpm check` green; `pnpm e2e` 19/19, including the new done-check test (reload restores ETHUSD 1h; a fresh browser with the same session gets it from the server; a second account gets the defaults); preferences store contract tests ran against DynamoDB Local.
