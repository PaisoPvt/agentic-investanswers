## Goal
`pnpm freshness` watches a running environment (local or AWS) for a few minutes and reports, per instrument and per step, how long after each minute closes it is in storage, in the History API (cache first) and on an open chart, with pass or fail against configurable thresholds; run after each staging release.

## Plan
What I found:
- M1-11 already times close → stored and close → served inside `pnpm live`. That is the writer's own view. M2-07 is the reader's view, from outside, as a customer sees it: the same steps, measured by a separate process against the real endpoints.
- Every step is visible from outside with an agent key:
  - **open chart:** a `/live` subscription receives each minute's stored (not forming) bar;
  - **cache:** `GET /bars` returns the newest bar, which comes from the recent-bars cache first;
  - **storage:** raw has the minute.
- The storage step is read through the hydration stores (`@aia/hydration`), which apps/hydration may use (rule 8). On AWS that needs S3 read, so it is optional: without store access the report says "storage: not measured".

Steps:
1. **`pnpm freshness [--url http://127.0.0.1:8080] [--minutes 5] [--symbol BTCUSD ...]`** in `apps/hydration/src/freshness.ts`. The agent key comes from `AIA_FRESHNESS_KEY` (never printed).
   - It subscribes on `/live` for each instrument and 1m.
   - For each minute that closes while it watches, it records: when the stored bar arrived on the live connection (**chart**); when `GET /bars?tf=1m&limit=1` first returned that bar, polled every 250 ms from the close (**cache**); and, with store access, when the raw minute first existed, polled the same way (**storage**).
   - Times are measured from the minute's close (bar time + 60 s), on this machine's clock; the report prints the clock offset against the server's `Date` header, so a skewed clock is visible.
2. **Thresholds** in `config/freshness.json`, p95 per step in seconds, starter numbers: storage 5 s, cache 5 s, chart 5 s; changed without code. When OI-24 gives the promised delay, these become it.
3. **The report:**
   - a table per instrument and step: count, p50, p95, max, threshold, pass or fail;
   - minutes that never arrived, listed as failures;
   - written to the terminal and as Markdown and JSON under `reports/freshness/<date>-<env>.md` (git-ignored);
   - exit 0 when all pass, 1 when any fail, 2 on a setup error.
4. **Tests:**
   - the timing and percentile maths and the report table (pure);
   - a run against the e2e server's simulated live feed, driven by its `/e2e/trade` and `/e2e/store` routes, so stored minutes appear on time and one is held back to show a failure;
   - no network to AWS in tests.
5. **Docs:** architecture "Freshness (M2-07)", how to run it after a staging release, and CLAUDE.md's command list (`pnpm freshness` now exists).

Not in this task:
- the CloudWatch dashboard and alarms (M4-05, needs OI-24);
- running it automatically after deploys (with GitHub deploys, deferred).

**Surprises.**
- Storage reads later than the cache though it happens first: it is polled every second and each check lists the whole live day, so it is an upper bound. That is documented.
- A fake clock shared by concurrent polling loops must be a scheduler: time jumps to the next sleeper only once all are waiting, or every loop's sleep pushes time forward.
