# M4-04 Usage and audit records for every human and agent request

GitHub issue: #44
Lane: C      Depends on: M4-01      Owner inputs: none

## Goal
Every request a principal (human or agent) makes to the platform leaves one usage and audit record (who, what, when, outcome), and the records can be read back per user and per agent.

## Plan
What I found:
- The `audit` context exists but is empty.
- Each route resolves its own principal (`/bars`, `/plan`, `/instruments`, `/indicators*`, `/mcp`, `/live`), so nothing records requests today.
- `Principal` is `{ kind, id, owner? }`: a human's account id, or an agent's key id plus the account it acts for.
- DynamoDB is already in the stack and runs locally (DynamoDB Local), so no new AWS service is needed.

**What one record holds:**
- when, and how long it took;
- who: kind and id, plus the owning account for an agent; requests made before sign-in (sign-in, sign-up) are stored as `anonymous`;
- what: method and route pattern (`/bars`, not the full URL), plus the instrument, timeframe, indicator or MCP tool where there is one;
- the outcome: status code, and the error code when refused, for example `forbidden` or `rate_limited`;
- the client address.

Never stored: tokens, passwords, request bodies or full query strings. Health checks are not recorded.

Steps:
1. **`contexts/audit`:**
   - domain: the `UsageRecord` type and a pure function that builds one from what the platform knows;
   - application: `AuditLog` (record, query per subject), the `UsageRecordStorePort`, and a buffer that writes in batches (every second or every 25 records), so a request never waits on the write. A failed write is logged and retried once, then dropped: the request always goes through;
   - adapters: DynamoDB (writes in batches, queries a page per subject, newest first) and in-memory (tests and the e2e server). Vitest tests.
2. **Storage:** a separate table `aia-<env>-audit` (`pk` = `human#<id>` or `agent#<keyId>`, `sk` = time and request id; TTL), created by CDK and locally on start-up like the users table. The platform's task role may write it and query it, never delete.
3. **Recording in `apps/platform`:**
   - each route hands its resolved principal and details to the request (a small helper replaces the repeated `principals.resolve` call), and one `onResponse` hook writes the record. A `/live` connection is recorded when it opens and when it closes, with its subscriptions;
   - an MCP call is recorded as one record per tool call, with the tool name;
   - tests: one record per request type, the same for an agent and a human, refusals included, no tokens stored.
4. **Reading the records back:**
   - **`GET /usage?subject=me|<agentKeyId>&before=&limit=`** (contract types `UsageRecordView`, `UsageResponse`; this needs your approval). A signed-in user reads their own records, or those of one of their own agent keys, and never anyone else's. Agents may read their own. Paged like `/bars`. CloudFront also routes `/usage` (the infra route test enforces it).
   - **`pnpm audit --account <email or id> [--agent <keyId>] [--days 7]`** for you or an operator. It prints the records and totals per route and per day, read straight from DynamoDB (local or AWS profile).
5. **Retention:** records expire after **400 days** (TTL, set in config). This is a new decision record entry, since what to keep and for how long, including client addresses, is the client's call to confirm.
6. **Docs:** an architecture section (audit), the decision record entry, card handoff.

Not in this task:
- the CloudWatch dashboard (M4-05, needs OI-24);
- a usage page in the chart;
- per-plan quotas built on these records.
