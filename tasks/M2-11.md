## Plan
What I found:
- The chart and the API share one origin (CloudFront locally mirrored by the Vite proxy), so there is no CORS. Sign-in uses a bearer token in the chart's own localStorage, not cookies.
- Nothing sets `Content-Security-Policy`, `X-Frame-Options` or `frame-ancestors` today: **any site can frame the chart right now.**
- No owner input or decision mentions the client's site domain.

Choice: **iframe, not a web component.** An iframe keeps the chart on our origin: no CORS, the token never touches the client's page, and the domain lock is a single response header. A web component would run our code on the client's page, need CORS and a token handed across, and expose more of the bundle. It can come later if the client asks.

Steps:
1. **Allow-list as configuration**: `config/embed.json`, per environment (`local`, `dev`, `staging`, `prod`), a list of origins allowed to frame the chart. Local lists the e2e test page's origin; AWS dev lists none for now (only the chart itself); the client's domain is added when they give it.
2. **Domain lock at CloudFront**: a `ResponseHeadersPolicy` on the chart's default behaviour with `Content-Security-Policy: frame-ancestors 'self' <origins>`. `X-Frame-Options` cannot express an allow-list (ALLOW-FROM is obsolete), so it is set to `SAMEORIGIN` only when the list is empty, which browsers that understand CSP ignore anyway. API routes stay as they are (JSON, not framed). CloudFront response headers policies are part of CloudFront, not a new AWS service. Template test in `aia-stack.test.ts`.
3. **Same header locally**: Vite `preview` and `server` send the same CSP from `config/embed.json` (`local`), so e2e tests the real behaviour.
4. **Embed mode**: `?embed=1` gives a compact layout (no page header, chart fills the frame) and `?symbol=` / `?timeframe=` set the starting instrument and timeframe (ignored if the plan does not include them). Sign-in still happens inside the frame, as today.
5. **Our test page**: `apps/web-chart/embed-test/index.html`, a plain page that frames the chart, served on a different origin in e2e (a second static server). A second page on an origin not on the list.
6. **E2e**: new Playwright project `embed`: the chart loads and draws bars inside the allowed page; the browser refuses it inside the other page.
7. **Docs and records**:
   - Architecture: embed section (iframe, allow-list, header).
   - Decision record: new fallback "our own test page until the client's" and new temporary decision "iframe now, web component only if asked". Also note that browsers that partition third-party storage (Safari, Firefox, Brave) make users sign in inside the frame; single sign-on with the InvestAnswers site waits for OI-21.
   - Owner inputs: new OI-34 "the client's site origins to allow, and their test page", blocking nothing (fallback above).

Verify: `pnpm check`, `pnpm e2e`, `cdk synth` through the infra tests. After merge and deploy: check the header on https://d7rks7pj8vbkj.cloudfront.net with curl. Bars are not touched.
