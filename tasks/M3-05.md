**Question 1, where the SMA code lives (recommendation A):**
- **A (recommended): in the private repo, loaded at start-up.** The private repo gets a small package that exports `indicators: IndicatorDefinition[]` (the SMA). The platform loads the modules named in `AIA_INDICATORS` (paths, comma-separated) and registers what they export; without it, no indicator, as today. Public CI never sees the code; locally you clone the private repo next to this one. Deploy needs the private package in the container image, so a read-only token to the private repo (new owner input, with the AWS work).
- B: a git dependency in `package.json`. Public CI and every clone would fail without access to the private repo. Not recommended.
- C: the SMA in this public repo, as an exception to rule 5 (a textbook formula, nothing of InvestAnswers'). Simplest and tested in CI, but ATR (Phase 1) needs path A anyway, so the work is only postponed, and rule 5 gets an exception in the decision record.

**Steps (for A):**
1. **SMA package (private repo, by PR there):** `sma` definition: inputs `length` (whole number, 1 to 500, default 20) and `source` (default close); outputs a line "SMA" and markers "Long" and "Short" where the close crosses over or under the average (the demo strategy's entries, the same as `ta.crossover(close, s)` in OI-30's script). Warm-up bars draw nothing (`na`). Vitest tests worked by hand, including warm-up, ties and a cross on the first drawn bar. Its types are written against `@aia/indicators`' interface shape; the platform checks it at registration (`assertValidDefinition`).
2. **Loading (`apps/platform`):** `load-indicators.ts` reads `AIA_INDICATORS`, imports each module, checks each export and builds the `IndicatorRegistry`; a bad module stops start-up with a clear message (exit 2). Tests with fake modules.
3. **Engine wiring:** a bar source over `DataAccess` (`IndicatorBarSourcePort`: closed bars, newest `limit` or from a time), the Redis output cache (memory in tests and the e2e server), `IndicatorEngine` in `main.ts`.
4. **Contract addition (needs your OK):** `IndicatorOutputResponse { indicatorId, instrument, timeframe, settings, outputs: [{ key, label, kind }], points: [{ time, values }] }`, values already rounded to display precision (only drawn outputs, rule 5).
5. **Run route:** `POST /indicators/:id/outputs` with `{ instrument, timeframe, settings, limit }`. Principal first (401), read rate limit, the plan check for that instrument and timeframe exactly as `/bars` does (same 403 and upgrade link), `acceptSettings` (same 400), `limit` parsed as `HistoryQuery` does, then the engine. Tests on the server: plan refusals, invalid settings, unknown id, agent gets the same answers, response holds only declared outputs.
6. **Chart:** one KLineChart indicator template that draws server values by bar time (a line, and arrows for markers), with the legend "SMA 20". The Indicators menu adds the indicator; Apply in the dialog updates it; a Remove button takes it off. Outputs are fetched again when the instrument, timeframe or settings change, and when a bar closes. The forming bar has no SMA point until it closes (preview on the forming bar later, over the live connection). Pure mapping tested with Vitest.
7. **E2E:** the e2e server registers a test-only line indicator (in this repo's test support, not the SMA); Playwright adds it, sees its line on the chart, changes a setting, sees the line change, removes it.
8. **Agents (small, D-12):** the MCP tool "get indicator output", same query and checks as the route. Drop it if you'd rather keep this PR smaller.
9. **Docs:** architecture (loading indicator packages, run route), decision record (a new entry for path A, and D-11's progress), owner inputs (token for the private repo on deploy), card handoff. A local check: SMA 20 on BTC 1h from the real local stack, compared by hand with TradingView's SMA for a few bars (read-only, Claude in Chrome).

Not in this task: the backtest on the chart (signals into M3-06's engine are wired in M3-03's harness for parity); the forming-bar preview; per-plan indicator access (OI-21).

**Surprises.**
- KLineChart deep-merges an override's `extendData` (a Map became a plain object, and old points could survive a switch) and its default `shouldUpdate` only redraws when `extendData` changes. Points now live in `overlayPoints` by chart indicator id, `extendData` is a revision number, and the template recalculates on a new revision.
- Importing `klinecharts` needs a browser, so the template is in its own module (`output-template.ts`) and the mapping is tested without one.
- A stored 1h to 4h bar of the current period is partial; feeding it to the engine as closed would make every request a recompute ("last bar changed"). Hence the held-back forming bar.
- The MCP tool-list assertion in `mcp.test.ts` now lists five tools: two were added by this task, nothing was weakened.
- The dev AWS account switched to a new permission set, `AWSARKDeveloperAccess`; CDK is still not bootstrapped (OI-31 updated).
